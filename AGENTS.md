- Test: `dotnet test`
- Gate: `./build/gate.ps1` (the full gate CI runs) or `./build/gate.ps1 -Fast` (Debug, no pack): `dotnet tool restore`, the sample key, README samples and API map checks, each tested offline first, then the Definition of Done, `./build/dod.ps1`; it ends with `Definition of Done: PASSED`. ## Landing

How `/ship-plan` lands a reviewed plan. `integrate`: `pull-request` pushes the plan's branch and opens a pull request; `direct` pushes to the default branch. `release`: `none`; `tag` tags the plan's `Release:` version, or the next free one when another plan landed it first, and a plan has that line only when it changes something a release ships, such as the product's code, its package's readme or its build, so one that changes only site pages, CI, decision records, tests or repository docs lands with no tag and no release (ADR-0032 in `docs/decisions/project-template/`); when this project's releases ship something else, say what under `## Conventions`; `tag+release` also publishes a release from that version's section of `changelog`. On GitHub, `.github/workflows/tag-release.yml` tags and publishes it as the pull request merges, from the `Release:` line `/ship-plan` writes in its description or the changelog's newest section, and for a .NET library starts `.github/workflows/publish.yml`; `/ship-plan` run after the merge does only what that workflow didn't. `changelog`: the file every plan's last step writes, in the Keep a Changelog format, `CHANGELOG.md` by default. `pre-release`: `untracked` keeps the project pre-release until a version tag of 1.0.0 or later: nothing it released or stored has a reader that must keep working, so every text describes the product as it is, the changelog's `## [Unreleased]` is a catalog of what the product does that each plan edits in place, and a breaking change needs no deprecation or migration path, as ADR-0015 in `docs/decisions/project-template/` says; `tracked`, the default when the line is missing, tracks every change from the first release, for a project whose releases or stored data already have readers. `draft`: `no`, the default when the line is missing, which a template update never changes, so a project lands as it did; `yes` opens every pull request as a draft, as `/ship-plan draft` does, and a new project that runs NCode Review starts with it, since it reviews and approves a draft too, so marking it ready is the person's review; where NCode Review's approver is set up, which is where `.github/workflows/code-review.yml` passes `approve: true` and `approver-private-key` and the repository's `code-review` environment holds `NCODE_REVIEW_APPROVER_PRIVATE_KEY`, the NCode Review Approver submits that approval, and it meets the ruleset's required approval, of the last push, with one writer too; elsewhere NCode Review's own app approves, which counts for Scorecard but meets no required approval, which only someone with write access other than the author can give (ADR-0022, ADR-0034 and ADR-0036 in `docs/decisions/project-template/`); and `/run-issues` opens its pull requests as drafts either way. `follow-ups`: `issues` files a plan's follow-ups as issues in this repository; `<owner/repo>` files them in that repository; `none` files none, and `/ship-plan` lists them for you to record. `follow-up-label`: the label those issues get, `follow-up` by default; write a name with spaces as it is, such as `tech debt`. `gate`: `none`; a command, such as `./build/dod.ps1 -Fast`, that `/ship-plan`, `/run-issues`, `/address-feedback` and `/run-feedback` run from the repository root before each push, stopping when it exits non-zero or changes a file. `protect`: `none`; `hook` makes `.githooks/pre-push` refuse any push to the default branch, for a host that can't require pull requests, such as a private repository on GitHub Free. `pr-format`: `none`; `<file>#<heading>`, such as `AGENTS.md#Pull requests`, names the section that sets the title and description of the pull requests `/ship-plan` opens, which still end with their `Closes` lines. `review-bots`: the review bots, by login and separated by commas, whose findings `/run-issues`, `/address-feedback` and `/run-feedback` may fix, `ncode-review` by default, or `none`; `/run-issues` and `/run-feedback` judge every one of NCode Review's findings, whatever its severity, and fix each that holds, and a bot's finding alone never changes CI, the template, agent configuration, the build or the dependencies: `/address-feedback` and `/run-feedback` change them only when you approve it in their start question. `max-review-rounds`: `3`; after that many rounds of review feedback on a pull request, `/run-issues` and `/run-feedback` comment no further `/review`, so NCode Review isn't asked to review again, and still fix and answer every finding; they recommend the merge once every finding is fixed, declined or answered and the review of the last push they asked for is in. `board`: `none`; `<owner>/<number>`, such as `NCodeGroup/7`, names the GitHub Project whose Status columns, Backlog, Ready, In progress, In review and Done, show this project's stories, as ADR-0042 in `docs/decisions/project-template/` says: `/triage-issues` moves a ready story to Ready, a plan snapshot moves its issues to In progress, `/ship-plan` moves them to In review when it opens the pull request, and the board's own workflows move them to Done. The project template's `tools/kanban-board.mjs` sets a board up and prints this line. Each move needs the `gh` token's `project` scope, and a move that fails is reported and stops nothing. `prelude`: `none`; one PowerShell command that sets up the shell the workflow's commands run in, such as `./build/env.ps1`, a script in the repository, or `nvs use 26`, to put a tool installed through a version manager on `PATH`. `/ship-plan`, `/run-issues`, `/address-feedback` and `/run-feedback` run it before the gate, and executors and coordinators before each Done-when command, dot-sourced in the same PowerShell; a plan names it under Context for the executor, so no step repeats it. When it fails, they stop and show its error. Write it on one line, without a leading `. ` or `& ` operator, a `#` comment, or `;`, `|`, `&`, `&&` or `||`; `.template/Get-PlanState.ps1` prints any other value as `prelude=invalid`, and `/ship-plan` stops on it. `/run-issues` runs only when the host requires pull requests into the default branch, or `protect` is `hook` and the hooks are enabled.

## Conventions

- A public API change is recorded with `./build/Update-PublicApi.ps1`; the release that ships it runs it with `-Release`.
- Packages are published to nuget.org from a published GitHub release by `.github/workflows/publish.yml`, through nuget.org trusted publishing once a maintainer approves the protected `nuget` environment (ADR-0135 in `docs/decisions/project-template/`). The Landing section sets `release: tag+release`, so `.github/workflows/tag-release.yml` tags and publishes each release as its pull request merges and starts `publish.yml` (ADR-0016 and ADR-0137 in `docs/decisions/project-template/`).
- Package versions come from `version.json` through Nerdbank.GitVersioning (ADR-0138 in `docs/decisions/project-template/`): `version` is the version the next release ships, and the change that releases a version sets it to that version, so the release tag `v<version>` matches. `assemblyVersion` is `{ "precision": "major" }`, so every 6.x release carries AssemblyVersion `6.0.0.0` (ADR-0136 in `docs/decisions/project-template/`). `.github/workflows/publish.yml` checks out the tagged commit with the full history and packs a release with `-p:PublicRelease=true`.
- Package validation compares each pack with `PackageValidationBaselineVersion` in `Directory.Build.props`, the last version on nuget.org (ADR-0147 in `docs/decisions/project-template/`). After each stable release, `.github/workflows/raise-baseline.yml`, which `publish.yml` calls, pushes the branch that raises it and opens an issue whose link opens its pull request (ADR-0150 in `docs/decisions/project-template/`), so no plan raises it itself.
- CodeQL runs through `.github/workflows/codeql.yml`, CodeQL's advanced setup, so it analyzes pull requests from forks, which default setup skips, and the repository's code scanning settings keep default setup off ([ADR-1014](docs/decisions/1014-codeql-runs-through-a-workflow-of-the-repositorys-own-so-it-analyzes-pull-requests-from-forks.md)), which overrides project-template ADR-0020's SAST row. A language CodeQL analyzes that the repository adds goes into the workflow's matrix in the same change.
- This repository keeps `.github/workflows/code-review-auto-merge.yml` and accepts the template's ADR-0006 exception: it auto-merges only a Dependabot pull request whose one change is the NCode Review pin.
- `src/NCode.Disposables/README.md` is the package readme nuget.org shows, so its links are absolute; `README.md` is the repository's full guide.
- The C# samples in `README.md` and `src/NCode.Disposables/README.md` are copied by MarkdownSnippets from `tests/NCode.Disposables.Tests/ReadmeSamplesTests.cs` ([ADR-1000](docs/decisions/1000-readme-samples-are-compiled-tests-that-markdownsnippets-copies-into-the-readmes.md)): change a sample in its test, between `// begin-snippet: <name>` and `// end-snippet`, then run `dotnet mdsnippets`; never edit a README's `<!-- snippet: -->` block, which `./build/gate.ps1` checks against the tests. A `#region` name in a test needs a space.
- Releases of NCodeGroup/docs, the documentation site's toolchain, are adopted the day they are published while the NCode brand, the toolchain and the first sites built with them are built out ([ADR-1011](docs/decisions/1011-ncodegroup-docs-releases-are-taken-without-a-cooldown-during-the-build-out.md)), which overrides project-template ADR-0009's three-day cooldown for that one dependency: `.github/dependabot.yml` excludes it from the cooldown, until NCodeGroup/docs 1.0.0 or the maintainers end the build-out. Every other dependency, NCode Review included, waits three days.
- The documentation site's content is in `docs/site/`, and the shared toolchain in NCodeGroup/docs builds it ([ADR-1009](docs/decisions/1009-the-documentation-site-is-narrative-guides-built-by-a-shared-toolchain-outside-this-repository.md)): this repository gets no `package.json`, no lockfile and no Node.js code. A page is an `.mdx` file, never `.md`, listed in the `sidebar` of `docs/site/site.config.json`, with links to other pages written from the site's root with a trailing slash; the toolchain's `CONTRACT.md` is the reference. `.github/workflows/docs.yml` builds the site and checks its layout on every pull request, with the toolchain pinned by commit, and publishes it to GitHub Pages, https://disposables.ncode.io/, from every push to the default branch ([ADR-1012](docs/decisions/1012-the-documentation-site-is-published-to-github-pages-from-the-default-branch.md), [ADR-1013](docs/decisions/1013-the-documentation-site-is-served-at-disposables-ncode-io.md)). The READMEs link to it with that absolute URL, since nuget.org shows the package READMEs.
- A page never holds C# that must compile: it includes a sample with an empty `cs snippet=<Key>` code block, and the site's build fills it ([ADR-1010](docs/decisions/1010-site-samples-are-compiled-tests-in-a-project-of-their-own-included-by-key-when-the-site-is-built.md)). Site samples are tests in `tests/NCode.Disposables.Site.Tests`, which cannot see the library's internal members: one class per page, named for the page's file in a folder named for the page's folder (`docs/site/guides/share-a-resource.mdx` has `Guides/ShareAResourceSamples.cs`), and one fact per sample, named `<Key>Sample_Runs`, with the sample between `// begin-snippet: <Key>` and `// end-snippet`, each alone on its line. A sample key is PascalCase letters and digits, defined once in the repository whatever its letter case; a site sample's key starts with `Site` and no README sample's does, and `./build/gate.ps1` checks the markers and all three rules. A page may also include a README sample by its key.
- A page never holds a copy of a repository file either: it shows the file, whole or from the line that holds one text to the line that holds another, with an empty `file=<path>` code block, such as `xml file=Directory.Build.props from="<ItemGroup" to="</ItemGroup>"`, which the site's build fills and links to those lines at the commit it was built from (NCodeGroup/docs `CONTRACT.md` section 4, NCodeGroup/docs ADR-1010). The site's components style themselves with the brand's public tokens: the `--nc-` colour roles, spacing, radii, borders, elevation, motion, focus, controls and font families, the type roles' `-stretch` and `-tracking` parts, and Starlight's `--sl-text-*` sizes, never a step of a colour ramp or of the type scale; the site's build fails a component that reads one, or a `--nc-` token the brand does not define (NCodeGroup/docs ADR-1012).
- A guide has a `## Pitfalls` section, which the `requiredHeadings` rule of `docs/site/site.config.json` requires; the site's build fails a guide without it (NCodeGroup/docs ADR-1011). The API map's data, `docs/site/_components/data/api-map.json`, lists every line of `src/NCode.Disposables/PublicAPI.Shipped.txt` in exactly one entry, and `./build/gate.ps1` checks it with `build/Assert-ApiMap.ps1`: a change that ships a public member adds its entry. A change to a disposable's behavior updates its outcome in `docs/site/_components/data/disposables.json`, which `/start/which-disposable/` and `/reference/behavior/` draw.
